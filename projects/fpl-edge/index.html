THE PROBLEM

Too much data.
Too many choices.

Every gameweek, an FPL manager weighs price, form, fixtures, injuries, rotation risk and squad rules, usually across several tabs and spreadsheets.

The hard part is not finding statistics. It is turning them into one defensible decision: who to buy, who to start, and who to captain.

THE APPROACH

From metrics to
manager decisions.

Compare players

Contextual side-by-side comparisons instead of leaning on a single statistic.

Understand value

Cost weighed against performance indicators to support deliberate transfers.

Plan the squad

Formation, lineup and rule validation in one workflow, so an invalid squad can't be saved.

PHASE 6 · WHAT I'M BUILDING NOW

IN DEVELOPMENT

A predictive layer
behind every pick.

Prediction models

A Python pipeline estimating expected minutes, expected points, injury or rotation risk, captain value and transfer value (xMinutes, xPoints, xRisk, xCaptain, xTransfer).

Direct-manipulation My Team

Tap or drag players to build a lineup, with the formation adapting as the squad changes.

Preference-aware recommendations

Suggestions respect a manager's preferred formation and style, not just raw point projections.

Tested core logic

The store, lineup, validation and recommendation modules are covered by tests, so fixes such as formation handling don't regress.

WHAT I LEARNED

Prediction is only
half the product.

A model that outputs an expected-points number is not yet useful to a manager. The value comes from where it appears: next to the player, inside the transfer flow, and constrained by the rules of the game.

Treating rule validation and user preferences as first-class features, not afterthoughts, has shaped how I structure the code and decide what to test.
